Estruturas de dados no VINDIX

Como usamos o que aprendemos na disciplina para deixar o sistema mais rápido, organizado e sem desperdício de memória.

Curso: Engenharia de Computação · UNISAL
Sistema: vindix.tech
Código: github.com/pifaculdade2025/vindix
01

O projeto

O VINDIX é um sistema para clínicas: agenda, sessões, financeiro e convênios. Cada clínica tem o seu próprio banco de dados, o que deixa os dados separados e seguros, mas exige cuidado com conexões e memória.

Hoje

O sistema já está funcionando em vindix.tech, e todas as estruturas abaixo já estão no código.

Próximos passos

  • Botão desfazer usando uma pilha.
  • Fila de e-mails que não se perde se o servidor reiniciar.
  • Heap para os alertas, se o volume crescer.
02 · FOCO PRINCIPAL

Onde usamos cada estrutura

Para cada estrutura: o que ela é, onde está no sistema e por que escolhemos ela.

Fila

primeiro a entrar, primeiro a sair

Onde: no financeiro. Se duas sessões forem registradas ao mesmo tempo, as duas poderiam usar a última vaga do mesmo pacote. Para evitar isso, cada clínica tem uma fila: as operações são feitas uma de cada vez, na ordem em que chegaram.

Clínica A:sessão→pagamento→sessão
Clínica B:pagamento← não espera a clínica A

Também usamos em: lista de espera de pacientes (quem chegou antes é chamado antes) e pacotes de sessões (o pacote mais antigo é usado primeiro).

Por que fila? Dinheiro precisa ser lançado na ordem certa. E como é uma fila por clínica, uma clínica não fica esperando a outra.

Pilha

último a entrar, primeiro a sair

Onde: no histórico de alterações. Toda mudança num cadastro fica salva, e a tela mostra da mais nova para a mais antiga, igual a uma pilha de pratos: o de cima é o último colocado.

topo →14:32 telefone14:10 endereço09:05 criação
Por que pilha? É o que permite criar o botão desfazer: tiramos a alteração do topo e voltamos o valor antigo. Só faz sentido desfazer da mais nova para a mais antiga.

Lista encadeada

itens ligados por ponteiros

Onde: nas conexões com o banco. Cada clínica precisa das suas conexões, mas deixar todas abertas gastaria memória demais. Usamos um cache LRU: guarda no máximo 50 clínicas e, quando enche, fecha a que está há mais tempo sem uso.

const poolsEmpresa = new LRUCache({
  max: 50,                                  // no máximo 50 clínicas
  dispose: (pool) => pool.destroy(),         // ao sair, fecha as conexões
  ttl: 30 * 60 * 1000                       // sem uso por 30 min, sai
});
Por que lista encadeada? Por dentro, o LRU é uma lista ligada em ordem de uso. Mover um item para a frente só troca ponteiros, sem precisar empurrar todos os outros como num vetor.

Tabela hash (Map e Set)

acha pela chave, sem percorrer tudo

Onde: em tudo que é consultado a cada acesso ao sistema:

  • Login: guarda por alguns segundos se o token do usuário ainda é válido, sem ir ao banco toda hora.
  • Google Agenda: códigos de uso único, que são apagados assim que usados.
  • Dados sensíveis: um Set diz na hora se o campo (CPF, diagnóstico) precisa ser criptografado.
Por que hash? Num vetor, para achar algo é preciso olhar item por item. Na tabela hash vamos direto na chave, com o mesmo tempo para 10 ou 10 mil itens.

Ordenação e busca

organizar e encontrar rápido

Ordenação: o painel de convênios mostra os alertas mais graves primeiro e, em caso de empate, por nome do paciente. Os relatórios (dias mais cheios, especialidades mais procuradas) também são rankings ordenados.

Busca: o banco usa índices em árvore, que funcionam como uma busca binária: a cada passo, metade dos dados é descartada. Por isso achar um paciente entre milhares é rápido.

Detalhe: na busca por nome, o sistema espera o usuário parar de digitar antes de pesquisar. Em vez de uma busca por letra, é feita uma por palavra.

Fila de prioridade

o mais importante sai primeiro

Onde: nas guias de convênio, o sistema sempre usa primeiro a guia que vence antes, para nenhuma vencer com sessões sobrando.

Por que não usamos heap (ainda)? Cada clínica tem poucos alertas e todos aparecem na tela, então ordenar a lista inteira é tão rápido quanto. O heap vale a pena quando a lista é grande e só os primeiros interessam.

Árvores e grafos

hierarquias e ligações

Árvore de permissões: o código tem dois dígitos, a tela e a ação.

1   Acesso total
├─ 10  Cadastros (tudo)
│   ├─ 11 ver    12 incluir
│   └─ 13 alterar  14 excluir
└─ 60  Financeiro (tudo)
    └─ 61 … 63

Para saber se alguém pode incluir um cadastro, o sistema sobe a árvore: tem o 12? Senão, o 10? Senão, o 1?

Grafo de vínculos: profissionais e pacientes são os pontos, e “atende na especialidade X” é a ligação entre eles.

Cada profissional só enxerga os pacientes ligados a ele no grafo.

Ler rápido ou inserir rápido?

Cada escolha depende do que mais acontece naquele ponto do sistema.

04

Cuidando da memória

O servidor fica ligado por semanas. Se uma estrutura só cresce, a memória acaba. Por isso cada uma tem uma regra:

Tamanho máximo

No máximo 50 clínicas com conexão aberta e só 3 avisos na tela por vez.

Prazo de validade

Códigos de uso único somem em 10 minutos, e o cache de login dura 30 segundos.

Liberar ao sair

Quando uma clínica sai do cache, as conexões dela são fechadas. É o free() que vimos em aula.

05

O que a disciplina mudou no projeto

Antes, usávamos vetores para quase tudo e consultávamos o banco a todo momento. A disciplina nos ensinou a perguntar: o que mais acontece aqui, ler ou inserir? E a escolher a estrutura certa para isso.

Também aprendemos que toda estrutura na memória precisa de um limite ou de uma forma de ser liberada, igual ao malloc e free vistos em sala.
