01

Contexto do projeto

O VINDIX é um sistema web de gestão para clínicas multidisciplinares (agenda, sessões, financeiro e convênios). O backend usa Node.js com banco Firebird, com um banco separado para cada clínica. Essa escolha de organização de dados define vários dos problemas tratados abaixo, principalmente o gerenciamento de conexões e de memória.

Estado atual

O sistema está em uso em vindix.tech, com todos os módulos funcionando. As estruturas descritas nas seções 02 a 04 já estão implementadas no código.

Próximos passos

  • Função desfazer usando o histórico como pilha.
  • Fila persistente para e-mails e sincronização com o Google.
  • Heap para alertas se o volume crescer.
  • Paginação por cursor no lugar de FIRST/SKIP.
02 · FOCO PRINCIPAL

Integração com a disciplina

Cada estrutura abaixo aparece em um ponto real do código do VINDIX. Para cada uma: onde está, qual problema resolve e por que ela, e não outra.

2.1 Filas (FIFO)

enfileirar O(1) · desenfileirar O(1)
clinica.js · front/js/app.js · consultas SQL

a) Fila de processamento do financeiro, uma por clínica

Duas sessões registradas ao mesmo tempo poderiam consumir a última vaga do mesmo pacote, ou dois pagamentos simultâneos passariam juntos pela conferência do saldo. A solução foi serializar as operações que mexem em saldo numa fila FIFO por empresa: cada operação é encadeada no fim da anterior.

// Uma fila por empresa: o lançamento de uma clínica não espera pelo de outra
const filasFinanceiro = new Map();            // empresa → último elemento da fila
export async function exclusivoFinanceiro(usuario, fn) {
    const [{ empresa }] = await getEmpresa(usuario);
    const anterior = filasFinanceiro.get(empresa) ?? Promise.resolve();
    const vez = anterior.then(fn, fn);          // entra no fim da fila
    const fim = vez.catch(() => {});
    filasFinanceiro.set(empresa, fim);         // novo "tail"
    fim.then(() => { if (filasFinanceiro.get(empresa) === fim) filasFinanceiro.delete(empresa); });
    return vez;
}
Clínica A:sessão #81→pagamento→sessão #82(tail)
Clínica B:pagamento← independente da A

Na prática é uma lista encadeada de promessas: o Map guarda só o ponteiro para o último nó (o tail), e cada nó aponta para o anterior via .then. Inserir no fim custa O(1) e não há vetor crescendo. Quando a fila esvazia, a entrada da empresa é removida do Map, então a memória usada é proporcional só às clínicas com operações em andamento.

Por que fila e não um lock global? Um lock único faria a clínica B esperar a clínica A. Com uma fila por chave, a exclusão mútua vale só onde há conflito real (o mesmo saldo). Por que fila e não pilha? Operações financeiras precisam ser aplicadas na ordem em que chegaram.

b) Lista de espera de pacientes e consumo de pacotes

A lista de espera é uma fila de domínio: ORDER BY L.DT_ENTRADA, L.ID, quem chegou primeiro é atendido primeiro, com o ID como desempate. O mesmo princípio vale para pacotes de sessões: a sessão é descontada do pacote mais antigo com saldo (ORDER BY P.DT_COMPRA, P.ID), o que evita que pacotes antigos fiquem esquecidos.

c) Buffer de notificações (toasts) com tamanho fixo

No frontend, as notificações formam um buffer FIFO limitado a CONFIG.MAX_TOASTS: quando chega uma nova e o limite foi atingido, as mais antigas saem primeiro. É o mesmo comportamento de um buffer circular de sensores IoT: memória constante, descartando o dado mais velho.

d) Proteção da fila de eventos do servidor

O Node.js processa requisições numa fila de eventos (event loop). O middleware toobusy-js mede o atraso dessa fila e responde 503 quando ela está saturada, e o express-rate-limit limita requisições por IP. Em vez de deixar a fila crescer sem limite (e a memória junto), o servidor rejeita cedo.

2.2 Pilhas (LIFO)

push O(1) · pop O(1)
conexaoBD.js (HISTORICO) · navegação do frontend

Toda alteração e exclusão gera linhas na tabela HISTORICO (tabela, campo, valor antigo, valor novo, usuário, data/hora). O visualizador de histórico mostra os eventos do mais recente para o mais antigo: o histórico de um registro é lido como uma pilha, em que o topo é a última alteração.

Essa organização é o que permite o próximo passo planejado, a função desfazer: desempilhar a alteração do topo e regravar o VALOR_ANTIGO. Só faz sentido desfazer na ordem inversa: desfazer uma alteração antiga sem desfazer as mais novas deixaria o registro inconsistente.

topo →14:32 telefone14:10 endereço09:05 criação← base

A navegação da SPA também se apoia na pilha de histórico do navegador. O VINDIX usa history.replaceState (substitui o topo) em vez de pushState (empilha), de propósito: trocar de tela pelo menu não deve encher a pilha do botão “voltar” com dezenas de entradas.

Pilha também aparece sem ser declarada: a função obterConexao tenta novamente de forma recursiva (até 5 vezes) quando o login no Firebird falha; cada tentativa ocupa um quadro na pilha de chamadas. O limite de tentativas é o que garante que essa pilha não cresça sem fim.

2.3 Listas encadeadas: o cache LRU de conexões

acesso O(1) · remoção do menos usado O(1)
conexaoBD.js · biblioteca lru-cache

Como cada clínica tem seu próprio arquivo de banco, cada uma precisa do seu pool de conexões (5 conexões). Manter um pool aberto para toda clínica cadastrada esgotaria memória e conexões do Firebird. Criar e destruir a cada requisição seria lento. A solução foi um cache LRU (Least Recently Used):

const poolsEmpresa = new LRUCache({
  max: 50,                            // no máximo 50 clínicas com pool aberto
  dispose: (pool, key) => { pool.destroy(); },  // ao sair do cache, libera as conexões
  ttl: 1000 * 60 * 30                  // pool sem uso por 30 min expira
});

Internamente, um LRU combina duas estruturas:

  • Tabela hash (caminho do banco → nó): encontra o pool em O(1).
  • Lista duplamente encadeada ordenada por uso: a cada acesso o nó vai para a frente; quando o limite é atingido, remove-se o nó do fim (o menos usado) em O(1).

Por que lista encadeada e não vetor? Mover um elemento do meio de um vetor para o início custa O(n) (deslocar todos). Na lista duplamente encadeada basta religar 4 ponteiros. O número de clínicas ativas muda o tempo todo, e a lista cresce e encolhe sem realocação.

Ligação direta com alocação de memória: o dispose é o equivalente ao free() da aula. Sair da estrutura não basta; o recurso (as conexões TCP com o banco) precisa ser liberado explicitamente, senão haveria vazamento.

2.4 Tabelas hash (Map e Set)

busca, inserção e remoção O(1) médio
auth.js · nonces.js · agenda.js · regras.js · funcoes.js

É a estrutura mais usada no backend, sempre no caminho que roda a cada requisição:

OndeEstruturaO que resolve
auth.js · cacheTokenVersionMap id → versão (TTL 30 s)Cada requisição valida se o JWT ainda é válido (senha trocada ou logout invalidam a versão). O cache evita uma consulta ao banco por requisição.
auth.js · ROTAS_DURANTE_TROCASetUsuário com senha temporária só acessa certas rotas. Verificar “rota ∈ conjunto” é O(1), contra O(n) de percorrer um vetor.
nonces.jsMap nonce → {usuário, expira}Tokens de uso único no fluxo OAuth do Google: consulta e remoção em O(1) (get + delete), impedindo reuso do mesmo link.
agenda.js · tokenPorUsuarioMap usuário → promessa do tokenSincronizar uma série inteira de agendamentos usa um só token do Google: as demais chamadas aguardam a mesma promessa.
regras.js · CAMPOS_CRIPTOGRAFADOSSet por tabelaDecide em O(1) se um campo (CPF, diagnóstico, evolução) deve ser criptografado antes de gravar.
funcoes.js / convenios.jsnew Set(ids), new Map(lista)Remover IDs duplicados e “juntar” listas em memória (ex.: id → nome do convênio) em O(n), em vez de O(n²) com laços aninhados.
 
export function consumirNonce(nonce) {
    const entry = nonces.get(nonce);      // O(1)
    if (!entry) return null;
    nonces.delete(nonce);                  // uso único
    if (Date.now() > entry.expira) return null;
    return entry.usuario;
}
Hash de tabela ≠ hash criptográfico. O projeto usa os dois e eles têm objetivos opostos. A tabela hash quer ser rápida (O(1)). Para senhas usamos bcrypt, que é lento de propósito (custo configurável por SALT_ROUNDS) para dificultar força bruta. Códigos de recuperação de senha são guardados como SHA-256, nunca em texto puro. O login também compara contra um hash falso quando o usuário não existe, para que o tempo de resposta não revele quais logins são válidos.

2.5 Ordenação e busca

ordenação O(n log n) · busca indexada O(log n)
convenios.js · relatórios · índices do Firebird · front/js/app.js

Ordenação multicritério para ranking de alertas

O painel de convênios gera alertas (guia ausente, sessões agendadas acima do saldo, guia acabando ou vencendo) e precisa mostrar os mais graves primeiro:

alertas.sort((a, b) =>
    b.gravidade - a.gravidade                                   // 1º: gravidade (decrescente)
 || String(a.paciente).localeCompare(String(b.paciente), 'pt-BR')); // 2º: nome (A–Z, com acentos)

O Array.prototype.sort do V8 usa TimSort (híbrido de merge sort e insertion sort): O(n log n) no pior caso e estável. A estabilidade importa quando se ordena por um critério depois do outro. O localeCompare('pt-BR') garante que “Álvaro” fique junto de “Alice”, e não depois de “Zélia” como aconteceria comparando códigos Unicode.

Os rankings dos relatórios (demanda por especialidade, horários de pico, carga por profissional, formas de pagamento) seguem o mesmo padrão: agregação no banco (GROUP BY) e ordenação do resultado já reduzido.

Busca: índices B-tree do banco

As buscas por chave (paciente por ID, consultas por data, guias por validade) são resolvidas pelos índices do Firebird, que são árvores B. A árvore B é a generalização da busca binária para disco: cada nó tem muitas chaves, a árvore fica rasa e cada consulta lê poucas páginas (pageSize: 4096). Localizar um registro entre milhões custa O(log n).

No frontend, a busca por nome usa debounce de 300 ms: a consulta só é enviada quando o usuário para de digitar, reduzindo de uma requisição por tecla para uma por palavra.

Onde a busca binária aparece de verdade: qualquer lista já ordenada (como o log de histórico, gravado em ordem de data/hora) permite localizar um instante em O(log n) dividindo o intervalo ao meio. É o que o índice faz por nós; reescrever isso em JavaScript sobre dados que já estão indexados no banco seria duplicar trabalho.

2.6 Filas de prioridade

heap: inserir O(log n) · extrair máx. O(log n)
clinica.js (guias) · convenios.js (alertas)

Dois pontos do sistema são, conceitualmente, filas de prioridade:

  • Escolha da guia de convênio: a sessão usa a guia com vaga que vence antes (ORDER BY COALESCE(G.VALIDADE, '9999-12-31'), G.DT_EMISSAO + FIRST 1). É uma extração do mínimo: a prioridade é a data de validade, para que nenhuma guia expire com sessões sobrando.
  • Alertas críticos: a gravidade (1 a 3) é a prioridade.
Decisão de trade-off: por que ainda não usamos um heap. Para a guia, o índice do banco já entrega o mínimo sem carregar todas as guias. Para os alertas, a lista de uma clínica tem dezenas de itens e é exibida inteira: ordenar tudo custa O(n log n), o mesmo que montar um heap e extrair n elementos. O heap só ganha quando interessam os k primeiros de um n grande (O(n + k log n)), ou quando itens chegam continuamente, como num sistema de alarmes em tempo real. Esse é o gatilho registrado nos próximos passos.

2.7 Árvores e grafos

hierarquias e relacionamentos
Observacoes.txt (permissões) · vínculos · DOM

Árvore de permissões

As permissões são codificadas em dois dígitos: o primeiro é a tabela, o segundo a ação. Isso forma uma hierarquia de três níveis:

1  Acesso geral (raiz: dispensa todas)
├─ 10 Cadastros · geral
│   ├─ 11 acessar  12 inserir  13 alterar
│   └─ 14 excluir  15 histórico
├─ 20 Consultas · geral → 21…25
├─ 40 Agendamentos · geral → 41…45
└─ 60 Financeiro · geral → 61…63

Verificar uma permissão é subir a árvore: tem a folha (ex.: 12)? Senão, tem o nó da tabela (10)? Senão, tem a raiz (1)? São no máximo três testes de pertinência no vetor de permissões do usuário (permissoes.includes). Aqui um vetor é adequado: cada usuário tem poucas dezenas de permissões, então O(n) com n pequeno é tão rápido quanto um Set e mais simples de serializar.

Grafo de vínculos

Os vínculos “profissional atende paciente na especialidade X” formam um grafo bipartido entre profissionais e pacientes, com arestas rotuladas pela especialidade. É esse grafo que define o que cada profissional enxerga: um usuário ligado a um profissional só vê os pacientes adjacentes a ele.

O frontend monta essas adjacências como listas em Map (paciente → especialidades permitidas) para filtrar os selects em cascata do agendamento sem novas idas ao servidor.

Hierarquia multi-tenant

Banco principal → empresas → registros de cada clínica: outra árvore, que dá o isolamento entre clientes.

04

Gerenciamento de memória

Um servidor Node.js roda por semanas sem reiniciar. Qualquer estrutura em memória que só cresce vira um vazamento. Todas as estruturas do VINDIX têm um limite ou uma rotina de limpeza:

Limite de tamanho

LRU com no máximo 50 pools; tokenPorUsuario é esvaziado acima de 5.000 entradas; corpo de requisição limitado a 100 KB; buffer de notificações com tamanho fixo.

Expiração (TTL)

Nonces expiram em 10 min e uma varredura a cada 5 min remove os vencidos; cache de versão de token dura 30 s; pools ociosos expiram em 30 min.

Liberação explícita

dispose → pool.destroy() fecha conexões ao sair do cache; a fila financeira apaga a chave da empresa quando esvazia; timers de limpeza usam .unref() para não prender o processo.

É a mesma disciplina do malloc/free vista em C, aplicada num ambiente com coletor de lixo: o coletor só libera o que nenhuma estrutura referencia mais. Se um Map global mantém a referência, o objeto nunca é coletado. Por isso a remoção precisa ser feita no código.

05

Como a disciplina ajudou no PI

Antes

As primeiras versões usavam vetores para quase tudo e consultavam o banco sempre que precisavam de algo. Funcionava com poucos dados, mas não havia critério para saber por que algo ficaria lento ou consumiria memória.

Depois

A análise assintótica deu um vocabulário para decidir: identificar a operação dominante, escolher a estrutura que a torna O(1) ou O(log n) e aceitar conscientemente o custo nas demais. Os conceitos de ponteiros e alocação explicaram o funcionamento do LRU e da fila encadeada de promessas, e deixaram claro que toda estrutura em memória precisa de uma política de liberação.

O resultado é um sistema em que as decisões de arquitetura podem ser justificadas: hash onde a leitura domina, fila onde a ordem importa, lista encadeada onde o conjunto muda o tempo todo, árvores onde há hierarquia ou busca em disco, e ordenação simples onde um heap não traria ganho.
